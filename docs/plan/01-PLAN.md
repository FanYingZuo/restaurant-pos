## 1 目標與範圍

**定位**：作品集。展示後端設計、交易與併發、測試與完整交付。單一門市、單一實例。

| 面向 | 內容 |
| --- | --- |
| 顧客（手機） | 掃桌上 QR 點餐、查看本桌訂單與出餐狀態 |
| 服務員（POS 平板） | 開桌、點餐、出單、修改、取消、結帳、作廢、日結 |
| 廚房（KDS 平板） | K1／K2 各看自己的品項，更新製作狀態 |

**要做**：員工（PIN 打卡、員工管理、管理者解鎖、出勤更正）／裝置（配對、憑證、撤銷）／菜單（分類、品項、選項群組、選項、售完、上下架、圖片、排序）／桌位（版面、開桌、QR、人數、服務費開關）／訂單（草稿、出單、修改、取消品項／整單／開桌）／結帳（開始、現金、部分付款、退回、放棄、作廢、收據）／廚房（站別清單、狀態變更、WebSocket 推播）／報表（營業額、今日總覽、日結、工時）／稽核／出單機（QR 單、廚房單、修改單、取消單、收據的列印與重印）。

**不做**：低消、折扣、移桌、併桌、拆單結帳、外送、外帶（結構預留）、會員、信用卡、行動支付、電子發票（付款保留擴充點）、多門市、多實例、離線模式、顧客單需店員確認（保留擴充點）、通知系統、報表匯出檔案、刪除班次（只能更正）。

**範圍外（另案）**：部署上線（店內主機與網段、反向代理、HTTPS 憑證、WiFi 網段切分、備份還原、真實印表機連接）。本規劃在開發環境完成並通過驗收即結束。

**開發順序**：第一部分 後端・平板（S0～S10）→ 第二部分 後端・出單機（S11）→ 第三部分 前端（S12～S16）。

## 2 開發原則

1. **現階段不花錢**（不可妥協）：不用任何付費服務、軟體、硬體。
2. **一次一張卡**（不可妥協）：每張卡完成後停下回報；階段驗收卡通過且使用者回「好」才進下一階段。
3. **先後端再前端**：前端需要的資料在 S1 以「畫面清單＋API 合約」先凍結。
4. **先平板再出單機**：兩者用事件切開，加出單機時不改業務程式。
5. **規格先行**：規格沒寫或矛盾 → 停下記待決，不自行決定。
6. **測試先行**：先列測試情境，使用者確認後才寫測試與實作；確認後的測試不得為了通過而修改。

**角色**：使用者負責規格、決策、確認；程式與測試由 AI 依本文件與 `02-TODO.md` 產生。

### 4.3 型別與資料庫規則

- **主鍵**：整數自動遞增；實體間用主鍵參照，不用 JPA 自動關聯。
- **金額**：整數元；DB `DECIMAL(12,2)` 但值一律整數；程式內用精確小數；價格含稅。
- **時間**：一律 UTC 瞬時點 `DATETIME(6)`；JDBC 與 Hibernate 時區明設 UTC，須有「寫入讀出不位移」測試；畫面再轉台北時間。
- **營業日**：日期（不含時間）。狀態欄位存文字，不用 DB 列舉。
- **命名**：DB 小寫底線、程式駝峰。軟刪除記刪除時間，所有查詢排除已刪除。
- **實體**：狀態變更寫成實體方法，不在服務層到處設值。
- **DB 規則**：啟動時驗證實體與資料表相符，不符則啟動失敗不自動改表；不用觸發器、預存程序、DB 排程；隔離等級 REPEATABLE READ；悲觀鎖條件必須命中主鍵或唯一索引；寫入必須能在交易中完整回滾。
- **索引後補**（效能不足時以新遷移檔加）：品項的菜單參照、付款的付款方式、帳單的 Session 參照、用餐紀錄的（營業日，狀態）。

### 4.4 API 共通規則

- **回應**：JSON、欄位駝峰；成功直接回物件或陣列不包外層；null 照樣輸出；不回實體；ID 為數字；帳單號三位數補零字串；時間 ISO-8601 UTC；營業日 年-月-日；列舉大寫字串。
- **字串**：先去頭尾空白；選填空白視為未提供；超長度上限為驗證錯誤。
- **金額輸入**：只接受整數元。價格有小數 → `INVALID_PRICE`；付款有小數 → `PAYMENT_AMOUNT_INVALID`。**前端傳來的價格、小計、總額一律不採用**，只接受品項 ID 與選項 ID。
- **分頁**：頁碼預設 0（負數視為 0），每頁預設 10、最大 100；回應含內容、頁碼、每頁筆數、總筆數、總頁數；預設依 ID 遞增，菜單與報表依顯示順序。
- **時間與營業日**：「現在」只能來自注入的時鐘；營業日時區台北、每天 04:00 切換，在資料建立時寫入之後不重算；單號歸零、報表、今日售完、工時、打卡歷史都以營業日計算。
- **驗證順序**：先格式後業務；同時違反多條依各 API 規格順序回第一個錯誤。PIN 一般在鎖之前驗證；需避免「用錯誤 PIN 探測資料狀態」時，在狀態檢查之後驗證。

### 4.5 權限與安全

**核心原則**：POS 與廚房沒有「無驗證」的 API；所有店內 API 都必須帶裝置憑證（顧客可能和 POS 同網路）。

| 層級 | 做法 | 適用 |
| --- | --- | --- |
| 裝置憑證 | HTTP：標頭 `X-Device-Token`。WebSocket：`/ws` 的 HTTP 握手放行，憑證放 **STOMP CONNECT 帧的 `X-Device-Token`**，CONNECT 時驗證、失敗斷線，不放網址參數 | `/api/pos`、`/api/kds`、`/api/staff`、`/ws`。**唯一例外：配對 API** |
| PIN（記名） | 請求帶 PIN，服務內比對得出員工 | 打卡、取消品項／整單／開桌、作廢、退回付款、結束不收費、**日結存檔**（預覽免 PIN）、改服務費開關 |
| 管理者解鎖 | 管理者 PIN 換單一功能憑證 `X-Unlock-Token` | EMPLOYEE_MANAGE、TABLE_LAYOUT、DEVICE_MANAGE |
| 顧客 token | 標頭 `X-Session-Token` | 顧客端帶 Session 的 API |

- 層級疊加：取消品項＝裝置＋PIN；員工管理＝裝置＋解鎖。裝置分 POS、KDS；KDS 只能呼叫 `/api/kds` 與訂閱 `/ws`。
- 配對 API 路徑在 S1 合約定義，並在 Security 設定明列豁免。顧客菜單與菜單圖片不需驗證。

**PIN**
- 4～6 位數字，全店唯一（只比對在職員工）；伺服器密鑰 HMAC-SHA256，存 64 字元十六進位。
- 密鑰來自環境變數；正式環境必填且 ≥32 字元；開發未設定時用開發密鑰並印警告。密鑰無法輪替，外洩時「換密鑰＋全員重設 PIN」。
- 員工停用時 PIN 雜湊清空，驗證回「PIN 錯誤」，**不洩漏「已停用」**。
- 防暴力**以裝置計算**：同裝置 5 分鐘內錯 5 次 → 該裝置鎖 5 分鐘（含正確 PIN 也回「嘗試次數過多」）；成功不清計數；計數在記憶體；每次鎖定寫稽核。
- 所有「用 PIN 找員工」都經過同一個驗證元件。
- 首位管理者：啟動時沒有在職管理者就建立「店長」，PIN 來自環境變數；未設定則產生隨機六位數，**只印在主控台一次**。

**管理者解鎖**
- 管理者 PIN＋功能代碼 → 32 位元組隨機憑證（網址安全 base64），存記憶體、只對該功能有效；非管理者回 `NOT_MANAGER`；功能代碼不符回 `FORBIDDEN`。
- 失效：呼叫釋放 API（離開頁面）、閒置 30 分鐘、解鎖者停用或不再是管理者、服務重啟。

**裝置配對與憑證**
1. 管理者在已配對 POS 解鎖 DEVICE_MANAGE，建立裝置（名稱、類型）。
2. 後端回一次性配對碼（8 位英數字、10 分鐘有效）。
3. 新裝置以配對碼呼叫配對 API 取得 32 位元組憑證，**只回傳這一次**；配對碼立即失效。
4. DB 只存憑證的 HMAC 雜湊：**共用 PIN 密鑰**＋用途前綴 `HMAC(密鑰, "device:" + 憑證)`，不新增環境變數。錯誤**不區分「不存在」與「已撤銷」**。
5. 最後使用時間以分鐘為單位更新。
6. 配對錯誤以來源 IP 計算：10 分鐘內錯 10 次鎖 10 分鐘。
7. 首次啟動沒有任何裝置時自動建立一台 POS，配對碼**只印在主控台一次**。
8. 撤銷立即生效；WebSocket **每次心跳重新檢查**裝置，撤銷後斷線；不可撤銷自己正在用的裝置。

**顧客 token**
- 每個用餐紀錄一組，32 位元組安全隨機數。
- **不出現在任何 API 的文字回應**；只存在於 QR 圖片（S4）與 QR 列印單（S11）。
- 放在 QR 網址片段 `#t=`（瀏覽器不送伺服器）；前端讀出後用 `history.replaceState` 清掉，之後放標頭送出。
- 常數時間比對；**不存在的用餐紀錄與 token 錯誤回完全相同的內容**。

**HTTP 與環境**
- 無狀態、關閉 CSRF；只放行 `/api`、錯誤頁、`/ws`。
- 回應標頭：CSP 預設不允許任何來源、禁止嵌入框架、不送參照來源、禁止猜測內容類型。
- 應用程式只綁 127.0.0.1；只採信「信任代理」送來的 X-Forwarded-For；來源 IP 只用於日誌與配對防暴力；WebSocket 只允許公開基底網址的來源。
- **預設為正式環境**，只有明確設為開發才是開發；Swagger 只在開發啟用，正式路徑回 404。

**機密與防濫用**
- PIN、各種憑證、配對碼、密鑰不寫進日誌、回應、測試快照或錯誤訊息（細則見 `03-BOUNDARIES.md` 第 3 節）。
- 不信任前端的權限宣告；所有輸入都有格式驗證與長度上限。
- 顧客端：單張最多 30 項、單一用餐紀錄最多 50 張正式單、同一用餐紀錄送單至少間隔 1 秒（以 DB 上次送單時間判斷）；不做 IP 速率限制。

**稽核紀錄**
- 記錄：品項價格與選項加價變更、服務費開關、放棄結帳、退回付款、結束不收費、出勤更正、裝置配對與撤銷、管理者解鎖、PIN 鎖定。
- 欄位：時間、動作代碼、對象類型與編號、前值、後值、員工編號、裝置編號、理由。
- 與業務同一交易寫入；只新增；查詢需 EMPLOYEE_MANAGE。

### 4.6 併發、鎖、冪等與版本

**鎖的取得順序**（全系統固定，永遠由上往下）：用餐紀錄 → 桌位 → 每日帳單號流水 → 訂單 → 訂單品項 → 帳單 → 付款 → 員工。
- 改訂單、結帳、作廢、取消開桌前，交易開頭先鎖用餐紀錄；開桌先鎖桌位再處理流水。
- 要先查才知道用餐紀錄編號的，先做不鎖查詢，鎖住後**重新載入**再檢查。
- 鎖的方法統一命名「依編號查詢並鎖定」；鎖等待逾時 5 秒。

**編輯許可**：動到訂單的寫入先檢查「用餐紀錄使用中」與「非結帳中」。例外：廚房狀態變更不檢查結帳旗標，用餐紀錄「使用中」或「已結束」都可以，「已取消」拒絕。

| 冪等操作 | 冪等鍵 | 規則 |
| --- | --- | --- |
| 服務員送出草稿 | 請求編號（Session 內唯一） | 同編號 → 回原結果，不論內容 |
| 顧客送單 | 請求編號（Session 內唯一） | 同編號＋內容雜湊相同 → 回原結果；不同 → `DUPLICATE_REQUEST` |
| 付款 | 付款鍵（帳單內唯一） | 同鍵＋同內容 → 回目前帳單；不同 → `PAYMENT_IDEMPOTENCY_CONFLICT` |

- 請求編號與付款鍵：1～64 字，只允許英數字、底線、連字號。冪等檢查放在「過期」與「結帳旗標」之前。
- **版本號**：訂單品項版本初始 0，狀態／數量／選項／備註變更時 +1；訂單也有版本號。廚房狀態變更與修改品項必須帶預期版本，不符回 `CONCURRENT_MODIFICATION`。
- **衝突轉換**：唯一索引衝突、死結、鎖等待逾時一律轉 `CONCURRENT_MODIFICATION`，不自動重試。
- **併發保證**（必須有多執行緒測試）：同時開同一桌只一個成功；同時出單只一個成功且批次號不重複；同時付足額只一筆完成、不超收；同時送同一顧客請求編號只一張單。

### 4.7 事件與副作用

### 4.10 菜單圖片

1. 品項存在；檔案 ≤2 MB。
2. 以檔案開頭位元組判斷 JPEG 或 PNG，不信任副檔名與內容類型。
3. 先讀標頭寬高，超過 4000 像素直接拒絕，再完整解碼。
4. 重新編碼後儲存，去除 EXIF 等中繼資料。
5. 檔名由程式產生；讀取與刪除前先驗證鍵格式（防路徑穿越）。
6. 新圖儲存成功後才刪舊檔，刪檔失敗只記日誌；圖片回應帶「禁止猜測內容類型」與可快取標頭。

#### S2 員工、裝置與出勤

- **員工管理**（EMPLOYEE_MANAGE）：列表（不回 PIN）、新增、改名與角色、換 PIN、停用；至少保留一位在職管理者；角色只有員工與管理者。
- **管理者解鎖**：取得、釋放、閒置失效（§4.5）。
- **裝置管理**（DEVICE_MANAGE）：列表、建立並取得配對碼、重新產生配對碼、撤銷。
- **出勤更正**（EMPLOYEE_MANAGE）：補上班或下班時間、修改既有班次、新增完整班次；不能刪除；理由必填；下班晚於上班且不晚於現在；限 31 天內；不能改自己的（唯一管理者例外）；寫更正歷史與稽核；班次標記「已更正」。
- **稽核查詢 API**（EMPLOYEE_MANAGE，依日期與動作篩選）。
- **提供給其他模組**：PIN 驗證取得員工、解鎖憑證檢查、批次取員工名稱。

**完成條件**：員工、打卡、裝置、出勤更正、稽核查詢測試全部通過。

#### S3 菜單
- **欄位**：分類（名稱 1～50 字、顯示順序 0～9999、上下架）；品項（名稱 1～80 字、價格 0～9,999,999 整數、站別 K1／K2、售完營業日、圖片鍵）；選項群組（最少 0～20、最多 1～20、最少 ≤ 最多、是否允許重複）；選項（加價 0～9,999,999）。
- **可售判斷**（查詢時計算）：品項上架未刪除、分類上架未刪除、售完日不是今天、每個群組的選項數 ≥ 最少可選。
- **售完**：設為今天營業日，隔日自動恢復；可手動恢復；重新上架不清除售完日。
- **規則**：單層分類；全部軟刪除；分類下仍有上架品項不可下架、仍有品項不可刪；品項需先下架才可刪；刪群組連同選項軟刪除；改價改名不影響既有訂單。
- **排序**：提交的編號列表必須剛好等於該層所有未刪除項目，依位置從 0 重新編號。
- 圖片上傳、刪除、取圖（§4.10）。改價與選項加價寫稽核。
- **提供給訂單**：「可售品項快照」（不存在 → 找不到；不可售 → 不可售）與「可編輯品項」（只要求未刪除）；快照只含未刪除的群組與選項。
- **顧客菜單**：只含上架分類中的可售品項，空分類不出現，加價為 0 也回傳。

**完成條件**：菜單測試全部通過；顧客菜單可取得。

#### S4 桌位與用餐紀錄
- **桌位**（TABLE_LAYOUT）：桌號 1～20 字（不分大小寫、去空白後唯一）、容量 1～50、寬高 40～400、座標 0～5000、區域 0～32 字；方形與圓形高度等於寬度，送了不同寬高回 `VALIDATION_ERROR` 不自動修正；長方形獨立；使用中不可編輯或刪除；自然排序（A2 在 A10 前）。
- **用餐紀錄**：狀態 使用中／已結束／已取消；每桌同時最多一筆占桌的使用中；人數 1～99；帳單號每營業日從 1 開始、取消不回收。
- **開桌流程**：鎖桌位 → 檢查未使用 → 鎖並遞增當日流水 → 建立用餐紀錄（token、QR 到期 ＝ 開桌 +4 小時、服務費預設值）→ 桌位使用中 → 發佈用餐開始 → 回傳（**不含 token**）。
- **QR 圖片 API**（ZXing）：網址 ＝ 公開基底網址（去結尾斜線）＋訂單路徑＋用餐紀錄編號＋`#t=` token；只有使用中可取得。QR 有效期在查詢時判斷，不用排程。
- **修改人數與服務費**：使用中且非結帳中；服務費需 PIN 並寫稽核。
- **生命週期方法**（供其他模組，呼叫者先持有用餐紀錄的鎖）：結束、取消、重開。重開：原桌空著 → 占桌重開；原桌已被使用或已刪除 → **不占桌重開**並標記「待重新結帳」。
- 待重新結帳清單 API。

**完成條件**：桌位與用餐測試全部通過；開桌後可取得 QR 圖片。

#### S5 訂單
- **結構**：每個用餐紀錄最多一張草稿；送出後批次號 ＝ 該用餐紀錄最大批次 +1；來源為店員或顧客（顧客直接建立正式單）。
- **訂單狀態重算**（只看未取消品項，依序）：沒有 → 已取消；全部完成 → 已全部上餐；至少一項完成 → 部分上餐；至少一項製作中 → 製作中；其他 → 已送出。
- **品項狀態轉換**：待處理→製作中、待處理→已完成、製作中→已完成、待處理或製作中→已取消；已完成與已取消是終點。
- **金額與快照**：單價 ＝ 基本價 ＋ Σ（加價 × 數量）；小計 ＝ 單價 × 數量；建立時存名稱、價格、站別、選項快照；修改已送出品項時以目前菜單重建快照。
- **選項驗證**（依序）：數量 1～99 → 同一選項不重複 → 選項屬於品項的群組 → 每群「不同選項數」在最少與最多之間、不允許重複時數量不大於 1 → 依群組順序產生快照。
- **備註**：品項與訂單備註 0～255 字。
- **草稿**：新增、修改（整筆取代、價格以最新為準）、刪除（實體刪除）；不寫歷史、不發事件；變空時保留空草稿。
- **送出草稿**：驗證請求編號 → 鎖用餐紀錄 → 冪等重播 → 結帳中拒絕 → 空草稿拒絕 → 每項**重新**檢查可售與選項（任一失敗整張失敗）→ 轉正式單 → 寫歷史 → 發佈訂單送出 → 回批次號、品項數、是否重播。
- **修改已送出品項**：鎖後重新載入；草稿、結帳中、已取消、已完成、版本不符依序拒絕；製作中保持製作中；寫前後摘要歷史、重算狀態、發佈品項修改。修改訂單備註只寫歷史。
- **取消品項（PIN）**：狀態檢查之後才驗 PIN；已完成不可取消；記理由與操作員工。
- **取消整單（PIN）**：有任何已完成品項就不可取消；逐項取消並各自寫歷史、發事件。
- **取消開桌（PIN）**：有任何未取消的正式單品項就不可；實體刪除草稿、用餐紀錄已取消、桌位回空桌。
- **廚房品項狀態服務**：開始製作、完成；檢查順序：品項存在 → 站別符合 → 用餐紀錄使用中或已結束 → 未取消 → 版本相符 → 轉換合法；只發事件。
- **用餐詳情**：用餐紀錄、草稿、所有正式單（含已取消）、小計（只算正式單未取消品項，不含草稿與服務費）。
- **列印內容純函式**：廚房單、修改單、取消單的文字格式（見 S11），先寫好並測試，S11 才接上。

**完成條件**：訂單測試全部通過（含 §4.6 出單併發保證）；兩批訂單、修改、取消皆可用。

#### S6 廚房（KDS）
- 站別只有 K1、K2；路徑中的站別不存在 → 找不到。
- **清單規則**：站別符合；待處理或製作中；屬於正式單；用餐紀錄為使用中，或**今天營業日已結束**的（先付後吃）；已取消不列；依品項編號遞增；**一次查詢取回品項、選項、桌號，不在迴圈內逐筆查詢**。
- **清單內容**：品項編號、訂單編號、用餐紀錄編號、桌號、批次號、名稱、數量、備註、選項、狀態、版本、送出時間、訂單備註。
- **狀態變更 API**：開始製作、完成，帶預期版本，直接呼叫 S5 的品項狀態服務。
- **WebSocket（STOMP）**：端點 `/ws`；連線驗證依 §4.5，POS 與 KDS 皆可；主題每站一個（`/topic/kds/K1`、`/topic/kds/K2`）；用戶端只訂閱、傳入訊息忽略；伺服器每 25 秒心跳。
- **訊息種類**：品項新增或更新（完整資料）、品項移除（編號）、整板重新載入。
- **推播監聽器**：依 §4.7；重新讀取資料，讀不到就改送移除；推播失敗只記日誌。
- **可靠性契約**（前端遵守）：至少送一次、不保證順序；以「品項編號＋版本」去重，只套用版本 ≥ 目前版本的更新，移除一律套用；斷線重連後整份重新載入；每 60 秒定時對帳；60 秒沒收到訊息視為斷線。

**完成條件**：廚房測試全部通過；WebSocket 測試用戶端收到新增訊息；先付款後出餐時品項仍在清單上。

#### S7 結帳與付款
- **狀態**：帳單 結帳中／已完成／已作廢／已放棄（前兩者佔「有效帳單」位置）；付款 待處理／成功／失敗／已作廢／已退回。
- **金額**：小計 ＝ 明細加總；服務費 ＝ 小計 × 費率，HALF_UP 到整數（995 → 100、986 → 99）；折扣欄位保留為 0；總額 ＝ 小計 ＋ 費用 − 折扣；已付、找零、未付由成功付款計算。
- **快速金額**：{未付、向上取整到 100、500、1000} 去重排序（1096 → 1096、1100、1500、2000）；已付清回空列表。
- **開始結帳**：鎖用餐紀錄 → 已有結帳中帳單就直接回傳 → 草稿有品項拒絕 → 沒有可結帳品項拒絕 → 建立帳單（**含未完成品項**）、計算服務費 → 結帳旗標為真（之後訂單、人數、服務費都被鎖住）。
- **付款（可部分）**：冪等在狀態檢查之前 → 帳單必須結帳中 → 付款方式啟用且有處理器 → 實收 > 0 → 先建待處理付款 → 伺服器計算未付並呼叫處理器（前端不傳未付）→ 失敗：標失敗、**交易仍提交**、回 `PAYMENT_FAILED` → 成功：記入帳與找零 → 已付 ≥ 總額就完成帳單、結束用餐紀錄、發佈結帳完成。
- **現金入帳**：最多入帳到未付，超出為找零；不足就付多少入多少，可再付。
- **退回付款（PIN）**：帳單結帳中、付款成功 → 驗 PIN 與理由 → 處理器作廢（失敗整筆回滾）→ 付款已退回、扣回已付與找零 → 稽核。
- **放棄結帳**：還有成功付款就拒絕（先退回）；帳單標已放棄、紀錄全部保留、清除結帳旗標、寫稽核。
- **作廢（PIN）**：必須已完成且為今天營業日 → 驗 PIN 與理由 → 每筆成功付款呼叫作廢（任一失敗整筆回滾）→ 帳單與付款已作廢 → 用餐紀錄重開（S4 兩種重開）→ 發佈結帳作廢；之後依當下設定重新結帳。
- **待重新結帳的用餐紀錄**：不能點餐、改品項、改人數或服務費；可做結帳相關操作，或「結束不收費」（PIN＋理由＋稽核，狀態改已取消）。
- **收據預覽 API**：店名、桌號與帳單號、結帳時間（台北）、品項與金額、小計、服務費（含費率）、總計、成功付款與找零；任何狀態都可預覽，未完成時省略付款區塊。收據文字由純函式產生，S11 直接用來列印。
- **付款方式擴充**：payment_method（代碼、名稱、啟用、排序）；處理器介面有付款、確認、作廢，以代碼註冊；本規劃只有現金處理器。

**完成條件**：結帳測試全部通過（含 §4.6 付款併發保證）；開桌到作廢全流程可用。

#### S8 顧客端
- **顧客驗證**：缺 token 或長度不符、用餐紀錄不存在、token 不符，一律回**完全相同**的 `SESSION_TOKEN_INVALID`；驗證本身不檢查狀態與過期。
- **API**：菜單與圖片（無驗證）、驗證用餐紀錄（狀態、桌號、到期時間、是否過期、是否可點餐、服務費開關）、送單、查看訂單。
- **可點餐**：使用中、未過期、非結帳中、不是待重新結帳。
- **送單流程**：token 驗證 → 鎖用餐紀錄並重新比對 token 與狀態 → 冪等（內容雜湊）→ 過期 → 結帳中 → 送單間隔 1 秒 → 單張超過 30 項或正式單已達 50 張回 `CUSTOMER_ORDER_LIMIT`（同一步檢查）→ 每項可售與選項驗證 → 建立正式單（來源顧客）→ 寫歷史 → 發佈訂單送出 → 201。
- 送單的商業規則放 **order 模組**，customer 只做 token 驗證與轉呼叫。
- **內容雜湊**：每品項組成「菜單品項編號,數量,品項備註」，後接 `|` 與依編號排序的「選項編號:數量」（逗號連接）；品項之間以 `;` 連接；最後加 `#` 與訂單備註；整串 SHA-256；請求編號不納入。例：`12,2,少辣|5:1,8:1;30,1,|#不要香菜`。
- **查看訂單**：該用餐紀錄所有正式單（含服務員送的），已取消品項標示；不含內部編號、版本、取消原因。
- 過期後可查看、不可送新單；同請求重送仍取得原結果。

**完成條件**：顧客端測試全部通過（含送單間隔、§4.6 顧客送單併發保證）；用 token 送單後 KDS 清單出現品項。

#### S9 報表與日結
- **日期範圍**：起訖皆為營業日且**都算在內**，最多 92 個營業日（相差 91 天可以、92 天不行）；起晚於訖或超過 → `INVALID_DATE_RANGE`。
- **營業額報表**（逐日，沒資料的日子也回 0，另有合計列）：桌數、人數、營業額（含服務費）、小計、服務費、作廢數、放棄數、退回付款數、取消品項數。
- **今日總覽**（即時、不快取）：今日營業額、使用中桌數、上班中人數。
- **日結**：預期現金 ＝ 備用金 ＋ 當日完成帳單的現金入帳（不含找零，依帳單營業日）；差額 ＝ 實點 − 預期。預覽與存檔用同一函式。**預覽免 PIN；存檔需 PIN**。不能日結未來；存檔時先檢查日期再驗 PIN；可重複日結、最新為準；不鎖資料。
- **工時報表**：依日、週（週一起算）、月分組，可依員工篩選；只計完整班次（含更正後完整的，標示「已更正」）；歸屬上班營業日；異常清單列出上班未打卡與下班未打卡；已停用員工名稱仍顯示。
- 聚合在 DB 完成；報表不改任何資料（日結存檔除外）。

**完成條件**：報表與日結測試全部通過。

#### S10 平板流程端到端驗收
一個測試類別依序走完，全程不依賴出單機：
1. 用首次啟動的配對碼配對 POS，再配對一台 KDS。
2. 解鎖員工管理，新增員工 B；B 上班打卡。
3. 解鎖桌位版面，建立桌位 A1。
4. 建立分類「麵食」、「牛肉麵」（150，K1）、選項群組「加料」（最少 0、最多 2、不可重複）、「加麵」（+20）、「加蛋」（+15）、「小菜」（60，K2）。
5. 開桌 A1（4 人）：帳單號 1，可取得 QR 圖片。
6. 顧客用 token 送單：牛肉麵 ×2（加麵）＋備註；KDS K1 清單 1 筆。
7. 服務員草稿小菜 ×1 送出：批次 2，K2 清單 1 筆。
8. 廚房：牛肉麵開始製作再完成；小菜直接完成。
9. 修改或取消已完成的小菜 → 失敗。
10. 再送一項小菜（批次 3），以 PIN 取消（理由「客人不要了」）。
11. 開始結帳：小計 400、服務費 40、總計 440、快速金額 440、500、1000。
12. 實收 200（未付 240），再實收 500（入帳 240、找零 260）：帳單完成、桌位空桌；收據預覽正確。
13. 營業額報表：桌數 1、人數 4、營業額 440、取消品項數 1。
14. 日結：備用金 3000、實點 3440 → 差額 0。
15. 以 PIN 作廢：用餐紀錄回使用中；再結帳付清；報表作廢數 1。
16. B 下班；工時報表有一筆完整班次。

**完成條件**：端到端測試通過；用 Swagger 手動走完第 5～12 步。

### 第二部分：後端・出單機（S11）

只新增列印監聽器與列印工作者，**不修改第一部分的業務程式**；印表機以寫入檔案模擬。

#### S11 列印工作表與列印流程
- **為什麼用 outbox**：提交後直接列印、失敗只記日誌，廚房單沒印出沒人知道；接真實印表機後，印表機慢或離線也會拖慢 API。
- **print_job 欄位**：編號、類型、目標（站別或收據印表機）、內容、狀態（待列印／已列印／失敗）、嘗試次數、下次嘗試時間、最後錯誤、來源（業務事件或手動重印）、相關編號、建立時間、列印時間。存**完整內容**（含 QR 網址的 token，重印需要）。
- **列印監聽器**（§4.7，提交前執行）：
  - 用餐開始 → QR 單：分隔線、桌號、帳單號、開桌時間（台北，到分鐘）、「請掃描下方連結點餐」、最後一行為網址。
  - 訂單送出 → 依站別分組的廚房單：表頭「桌號＋第幾批、時間」；品項行「數量＋名稱」，縮排列出選項與備註；有訂單備註時加在最後。
  - 品項修改 → 修改單（標註「修改後」）。
  - 品項取消 → 取消單（每項加取消原因）。
  - 結帳完成 → 收據（S7 的收據純函式）。
- 內容在建立時固定，重印內容完全相同。
- **列印工作者**（唯一背景執行）：每 2 秒取出「待列印且到了下次嘗試時間」的工作，依建立順序交給 PrintPort。
  - 成功 → 已列印。
  - 失敗 → 嘗試次數 +1、記錯誤摘要；第 1～4 次失敗後分別等待 5、15、30、60 秒（待決 #2 採建議選項 A）；**嘗試滿 5 次**仍失敗 → 失敗，不再自動重試。
  - 某一筆重試時不擋同目標後面的工作（取捨：重試成功的單可能較晚印出）。
  - 單一執行緒、單一實例、不需分散式鎖；重啟後未完成的工作自動繼續。
- **PrintPort 檔案實作**：寫入 `logs/print.log`，每筆附時間與類型；token 遮蔽為 `#t=****`。
- **列印問題 API**：列出失敗與等待超過 30 秒的工作；**不回傳內容**，只回類型、目標、狀態、嘗試次數、錯誤、時間。
- **重印 API**：建立一筆新工作（原工作保留）；「重印 QR」不產生新 token，用餐紀錄非使用中 → 用餐已結束；「重印收據」。
- **測試**：記憶體假列印，可設定「前 N 次失敗」；列印工作者在測試中手動觸發。

**完成條件**：S10 端到端加列印驗證（開桌有 QR 單、第 7 步有 K2 廚房單、第 10 步有取消單、第 12 步有收據，狀態皆已列印）；假列印設為失敗後重印一張收據、重試後成功；第一部分全部測試仍通過（證明業務程式未受影響）。

- 開始製作、完成按鈕（帶預期版本）。
- WebSocket 訂閱（CONNECT 帶裝置憑證）、依 S6 可靠性契約去重、斷線重連整份重新載入、每 60 秒定時對帳。

#### S15 顧客手機點餐
- 從網址片段讀取 token 後立即清除網址列。
- 菜單瀏覽、購物車、選項選擇、送單；多台手機可共用同桌訂單，未送出的購物車只存在自己的手機。

- QR 過期、結帳中、用餐已結束、送單太頻繁時的提示。

#### S16 出單機相關畫面與總驗收
- POS「列印問題」清單：失敗與等待過久的列印工作。
- 重印按鈕：重印單據、重印 QR、重印收據。

**實作時要特別注意**
- 用餐詳情的小計不含草稿、不含服務費。
- 結帳會把尚未完成的品項也納入帳單。
- 用餐取消後帳單號不回收。
- 跨營業日切換時間打卡會產生兩筆班次，可用出勤更正處理。
- 付款失敗是唯一「回錯誤但交易仍提交」的地方。
- 用餐紀錄可能「使用中但不占桌」，以桌位找用餐紀錄的邏輯都要考慮。
